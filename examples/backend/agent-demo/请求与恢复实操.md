# Agent 请求、数据与恢复实操

**适用环境：Python 3.12；Linux、macOS 或 Windows WSL。离线业务练习不需要 Redis；HTTP 工具练习需要本机回环端口；完整队列练习使用 Compose。**

以“登录后上传研究笔记并执行文本统计”为主线，观察请求、表记录、后台状态与 SSE 如何关联。准备环境见 [Demo 运行说明](README.md)，输入文件统一在 [inputs/backend](../../../inputs/backend/README.md)，脚本在 [scripts/backend](../../../scripts/backend/README.md)。

## 先选择需要观察的边界

| 路线 | 实际执行什么 | 用来回答什么问题 |
| --- | --- | --- |
| 独立案例脚本 | 真实 FastAPI 路由、Pydantic、SQLAlchemy、`jobs.execute`，进程内请求 | 输入是否被拒绝、状态怎样改变、记录是否重复 |
| 本机 HTTP 工具 | Uvicorn＋TCP／HTTP＋异步客户端 | 网络调用如何并发、超时、部分失败 |
| Compose 全链路 | API、PostgreSQL、Redis、Celery、dispatcher | 多进程投递、服务中断、重启后核对 |

第一种把 enqueue 替换为收集 run ID，之后显式调用 execute，便于读代码和重现业务；它不能证明 Redis 投递或 Celery 硬超时。第三种需要目标平台实际启动所有服务，不能用第一种结果代替。

## 1. 安装隔离依赖并运行固定案例

以下从仓库根目录执行，示例使用仓库内独立虚拟环境：

```bash
uv venv --python 3.12 examples/backend/agent-demo/.venv
uv pip install --python examples/backend/agent-demo/.venv/bin/python \
  -r examples/backend/agent-demo/requirements.lock.txt
source examples/backend/agent-demo/.venv/bin/activate
python scripts/backend/运行Agent案例.py --output-dir /tmp/agent-backend-lab
```

`/tmp/agent-backend-lab` 必须不存在；再次练习请选另一个新路径。脚本不覆盖旧库，不修改 Archeos／ALKEMIE 账号，也不需要填现有口令。它用随机密码创建两个临时教学账号，检查 A 的资源不能被 B 访问，然后退出会话。

输出目录里有：

```text
agent-backend-lab/
├── demo.db             # 实际写入的 SQLite 数据库
├── report.json         # 每个案例的结果；没有登录令牌
└── normal-events.sse   # 正常任务实际生成的完整 SSE 事件
```

脚本中的密码不打印，数据库中的哈希只用于该临时练习，不应把整个库提交到仓库。`report.json` 的 run ID、会话 ID 每次不同，不要求和文档示例一致。

## 2. 对照输入理解正常执行

[研究笔记样例.md](../../../inputs/backend/研究笔记样例.md) 是 UTF-8 文本，原文件 226 字节。脚本用 multipart 上传后取得附件 ID，并把它加入 [run-normal.json](../../../inputs/backend/run-normal.json)：

```json
{
  "prompt": "请统计这份研究笔记的文本。",
  "client_key": "backend-normal-001",
  "timeout_seconds": 5,
  "mode": "normal"
}
```

执行输入在 `jobs.generate` 中按 `prompt + "\n" + attachment.content` 合并。原样例合并后为 140 个 Python 字符、14 个按空白分词的项，输出应包含：

```text
教学 Agent：并发完成两个工具调用。输入共 140 个字符，按空白分词为 14 项。
这是一段确定性输出，可在 generate 中接入模型 SDK。
```

“空白分词项”只是 `text.split()` 的计数，不是中文词法分析，更不是模型 tokenizer 的 token 数。UTF-8 字节数和字符数也不同，改变换行或正文会改变计数。

单个正常 run 的顺序为：

```text
POST 返回 202 和 run_id
  → runs / user message / queued event 同事务写入
  → worker 条件领取，attempt=1，生成领取凭据与截止时间
  → trace start / trace end / 多条 delta
  → assistant message / succeeded / done 同事务写入
```

查看报告：

```bash
python -m json.tool /tmp/agent-backend-lab/report.json
```

normal 案例应为 `succeeded`、attempt 1、messages 2。消息是输入和最终输出各一条，delta 存在事件表中，不按每个分块创建一条对话消息。

## 3. 同一输入为何可以重复提交

脚本连续提交相同 normal 输入，得到同一个 run ID；再次 execute 不会再领取终态 run。随后改 prompt、保留 client_key，接口应返回 409。

这三件事分别由不同代码保证：

| 行为 | 代码与约束 |
| --- | --- |
| 相同提交找到原 run | `submit` 查询 conversation＋client_key |
| 并发相同提交不创建两条 | 数据库唯一约束处理 SELECT 后的竞争 |
| 同键不同内容被拒绝 | `same_request` 比较 prompt、附件、期限与 mode |
| 重复队列消息不重复执行 | `claim` 只领取允许状态 |
| 重复完成不重复写结果 | 当前 lease 校验＋消息唯一约束 |

前端每次新逻辑请求生成新键；网络断开后不确定是否提交成功，则复用原键重试。若前端每次重试都生成 UUID，服务器无法知道它们其实是同一个意图。

## 4. 输入校验、权限和任务错误分开看

以下结果来自不同阶段，不能统一显示成“系统出错”：

| 案例 | HTTP／run 结果 | 是否创建 run |
| --- | --- | --- |
| 无登录或已退出 | 401 | 不应继续业务处理 |
| B 查询 A 的 run／历史 | 404 | 不创建任何新记录 |
| `run-invalid.json` | 422，指出两个错误字段 | 否 |
| 同一幂等键换输入 | 409 | 返回冲突，不创建第二条 |
| `run-failure.json` | POST 202，之后 run failed | 是 |
| `run-timeout.json` | POST 202，之后 run timed_out | 是 |

422 的 `fields` 应是 `body.timeout_seconds` 和 `body.unexpected_option` 对应路径。密码等原始输入不随错误结构返回。失败 run 保留用户输入和错误码，便于解释失败发生在哪个阶段，但不创建成功的 assistant 回复。

## 5. 重试的三个可观察时刻

[run-retry.json](../../../inputs/backend/run-retry.json) 使用 `retry_once` 模式，第一轮在 delta 产生前抛出 TransientToolError：

```text
第一次 execute：running，attempt=1
  → retry_later：retry_wait，next_at=当前时间+2秒
  → 到期后 dispatch_once 再投递同一 run_id
第二次 execute：running，attempt=2
  → succeeded
```

案例脚本按真实 `next_at` 等待退避结束，不通过伪造成功状态跳过第二轮执行。完整服务中由独立 dispatcher 每 5 秒扫描，因此页面观察的等待时间还会包含扫描周期。

查看报告 retry 项，第一次状态为 retry_wait，最终状态 succeeded、attempt 2。若只启动 API 与 worker，漏掉 dispatcher，这个例子可能停留在 retry_wait；这正是独立核对进程需要被监控的原因。

## 6. 超时、取消与 worker 过期的区别

超时输入让生成阶段等待超过 1 秒，最终为 `timed_out/deadline_exceeded`。取消 queued 的案例在领取前设置取消，因此 attempt 仍为 0。两者都没有成功输出，但原因不同。

worker 过期案例只在全新练习库中进行以下故障注入：

```python
lease = claim(run_id)
with session() as db:
    db.get(Run, run_id).deadline = time.time() - 1
    db.commit()
dispatch_once(send)
```

恢复扫描应将其置为 `timed_out/lease_expired` 并使旧 lease 失效。随后脚本故意使用旧 lease 写 delta 与 succeeded，分别应被拒绝或不生效。报告出现 `late_write: rejected`，数据库中也不应出现对应 assistant。

这验证了过期状态核对与迟到写入防护；没有真的杀死 worker，不能由此推断操作系统的进程树终止、Redis 重投或外部副作用恢复全部成立。

## 7. 从 SQL 看整体一致性

在仓库根目录执行：

```bash
sqlite3 -header -column /tmp/agent-backend-lab/demo.db < inputs/backend/查看任务.sql
```

预期总共 6 条 run、8 条 messages：normal 和 retry 各两条消息，failure、timeout、queued cancel、expired worker 各保留一条输入。输入校验失败和幂等冲突没有额外 run。

SSE 文件可以直接阅读，也可检查 `event: done` 是否在完整流中出现：

```bash
head -n 24 /tmp/agent-backend-lab/normal-events.sse
tail -n 8 /tmp/agent-backend-lab/normal-events.sse
```

不要把事件数量当对话轮次数。刷新历史查询最终消息，重连运行视图按事件游标读取过程，二者分别提供不同信息。

## 8. 再用真实 HTTP 做工具并发练习

终端 A 在 Demo 目录启动：

```bash
uvicorn demo.tool_api:app --host 127.0.0.1 --port 8001
```

终端 B 在仓库根目录执行：

```bash
python scripts/backend/并发调用HTTP工具.py inputs/backend/tools-normal.json
python scripts/backend/并发调用HTTP工具.py inputs/backend/tools-partial.json
python scripts/backend/并发调用HTTP工具.py inputs/backend/tools-deadline.json
```

正常输入应得到 words 6、characters 35；混合输入应同时包含 ok、timeout 和 HTTP 503；总期限输入返回 deadline_exceeded。耗时受机器、连接与调度影响，不把精确毫秒数作为成功条件。细节见[异步与 HTTP 工具](../../../notes/后端工程/并发与任务/同步异步线程与进程.md)。验证后在终端 A 按 Ctrl-C 关闭自己的教学服务。

## 9. 在 Compose 中验证服务中断

按 [README](README.md) 启动完整 Demo，登录网页或使用 curl。每次用新的 client_key 创建逻辑任务：

1. `docker compose stop worker`，提交 normal，观察 queued；120 秒窗口内 `docker compose start worker`，确认最终成功且只有一个逻辑 run。
2. `docker compose stop redis` 后提交，检查数据库保留 queued 意图；启动 Redis，保持 worker 与 dispatcher 运行，确认补投。
3. 用 retry_once 观察第一次 retry_wait，再确认下一次 attempt 与最终输出。
4. 查询自己的 run 与其他账号资源，确保网络部署没有绕过认证与资源授权。

一次运行中已开始的 prefork 子进程、外部任务和数据库事务各自有不同生命周期。真实 crash 测试需要记录目标进程、开始时 run 状态、终止方式、外部任务状态和恢复后的最终记录，不用“容器退出了”代替这些证据。
