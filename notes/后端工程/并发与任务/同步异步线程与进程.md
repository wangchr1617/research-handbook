# 同步、异步、线程与进程

**适用环境：通用；可运行示例使用 Python 3.12。命令在本机或 WSL 的 Demo 目录执行。**

## 先看任务在等待什么

同步与异步描述调用怎样等待结果，线程与进程描述执行单元。它们不是四个互斥的方案：一个进程可以有多个线程，某个线程中运行事件循环，事件循环再调度多个协程。

| 方式 | 如何推进 | 适合场景 | 关键限制 |
| --- | --- | --- | --- |
| 同步调用 | 当前调用等待完成后继续 | 简单逻辑、同步库、独立 worker | 慢 I/O 会占用当前执行单元 |
| 异步协程 | `await` 时让其他协程运行 | 多个网络工具、数据库异步驱动、流式响应 | 阻塞函数仍会卡住事件循环 |
| 线程 | 同一进程多个执行流，共享内存 | 包装阻塞 I/O 库 | 共享状态需同步，取消难以终止已运行函数 |
| 进程 | 独立地址空间，由操作系统调度 | CPU 密集计算、独立后台 worker | 启动、序列化和通信开销较大 |

通常的 CPython 构建有 GIL，纯 Python CPU 密集循环用线程不一定更快；释放 GIL 的数值库和可选自由线程构建需要具体判断。多进程可使用多核，但需控制每个进程内部 BLAS 线程数，避免超额并行。

## `async` 不会把阻塞库变成异步库

```python
import asyncio
import time

async def bad():
    time.sleep(1)               # 卡住事件循环

async def good():
    await asyncio.sleep(1)      # 让出执行权

async def wrap_blocking_sdk():
    return await asyncio.to_thread(blocking_sdk_call)
```

最后一行的 `blocking_sdk_call` 是待替换的同步 SDK 函数。优先使用原生异步客户端；只能使用同步 I/O 库时再放入线程池。`to_thread()` 等待者被取消后，已经在线程中运行的函数可能继续执行，因此 SDK 本身仍需连接与读取超时。

FastAPI 的普通 `def` 路由通常在线程池执行，`async def` 路由直接运行在事件循环上；在异步路由中直接调用同步 SQLAlchemy 查询仍会阻塞。配套 Demo 普通数据库路由使用 `def`，SSE 的短查询用 `asyncio.to_thread()`，worker 内同步数据库操作由独立任务进程执行。

## 并发调用多个工具

依次 `await search()`、`await metadata()` 是串行等待。独立工具可以同时调度，两个各耗时约 1 秒的 I/O 调用，理想总耗时接近 1 秒，而非 2 秒。下面是基于 Archeos 多工具调用场景写成的独立例子：

```python
import asyncio

async def search():
    await asyncio.sleep(.2)
    return "文献检索完成"

async def metadata():
    await asyncio.sleep(.2)
    return "元数据查询完成"

async def main():
    async with asyncio.timeout(2):
        async with asyncio.TaskGroup() as group:
            a = group.create_task(search())
            b = group.create_task(metadata())
    print(a.result(), b.result())

if __name__ == "__main__":
    asyncio.run(main())
```

`TaskGroup` 退出时等待所有子任务。一个子任务出现未处理的普通异常，会取消其余任务，随后以 `ExceptionGroup` 报告。适合“任一必要工具失败则整组失败”。使用 `except* ValueError` 等分别处理异常组；不要在同一 `try` 中混用 `except` 与 `except*`。

如果允许部分结果，工具内部只捕获预期错误并返回结构化结果，或者有意识地使用 `gather(..., return_exceptions=True)`，逐项判断异常，不能把异常对象当成功结果。`gather()` 的默认异常传播也不等同于 `TaskGroup` 的兄弟任务取消策略。官方语义见 [asyncio Task 与 TaskGroup](https://docs.python.org/3.12/library/asyncio-task.html)。

## 并发上限、超时与取消

完整代码在 [demo/concurrency.py](../../../examples/backend/agent-demo/demo/concurrency.py)。它用 `Semaphore(2)` 限制同时进入的工具数量，用每工具 `asyncio.timeout()` 控制局部期限，再包一层总期限。示例局部超时包含等待并发名额的时间；如果只想限制工具真正执行时间，可把局部 timeout 放到 semaphore 内。

```bash
python -m demo.concurrency
```

正常结果包含两个 `ok` 和一个 `timeout`，随后输出 `cancelled and awaited`。也可以在 Python 中调用 `call_tools([("broken", .01, 1), ("other", 10, 20)])`，观察 `ExceptionGroup` 与兄弟任务取消。

取消必须有发出、传播和收尾三个步骤：

```python
task = asyncio.create_task(long_operation())
task.cancel()
try:
    await task
except asyncio.CancelledError:
    pass
```

在 `long_operation()` 内用 `finally` 释放连接、关闭迭代器、清理临时文件；若捕获 `CancelledError`，清理后应重新抛出。`cancel()` 是协作式请求，要到协程可被取消的位置才生效。`asyncio.timeout()` 在上下文边界将其超时取消转换成 `TimeoutError`，应在上下文外捕获。

`wait_for()` 等待取消清理时，实际返回时间可能超过名义超时。阻塞线程、子进程、远端作业和已发生的副作用都不会因为当前协程取消而自动消失。系统级硬限制和外部任务状态核查见[后台任务](后台任务队列与恢复.md)。

## CPU 计算怎样处理

CPU 密集函数可交给 `ProcessPoolExecutor` 或后台计算服务。函数必须定义在可导入模块顶层，输入输出可序列化；Windows／macOS 的进程启动方式尤其要求入口保护：

```python
from concurrent.futures import ProcessPoolExecutor

def square(x):
    return x * x

if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=2) as pool:
        print(list(pool.map(square, [1, 2, 3])))
```

这里的线程池、进程池仍属于当前应用生命周期。需要跨 API 重启继续运行、排队与恢复的 Agent 任务，应提交到[独立 worker](后台任务队列与恢复.md)。

## 从模拟等待走到真实 HTTP 工具

只用 `sleep()` 容易忽略连接、响应码与 JSON 解码。配套 [tool_api.py](../../../examples/backend/agent-demo/demo/tool_api.py) 启动一个本机工具服务，其中统计工具实际处理请求文本：

```python
@app.post("/tools/word-count")
async def word_count(body: ToolInput):
    await asyncio.sleep(body.delay_seconds)
    return {"words": len(body.text.split())}
```

在 Demo 目录启动服务，在仓库根目录用同一虚拟环境的 Python 运行客户端：

```bash
# 终端 A：examples/backend/agent-demo 目录。
uvicorn demo.tool_api:app --host 127.0.0.1 --port 8001
```

```bash
# 终端 B：research-handbook 根目录。
python scripts/backend/并发调用HTTP工具.py inputs/backend/tools-normal.json
python scripts/backend/并发调用HTTP工具.py inputs/backend/tools-partial.json
python scripts/backend/并发调用HTTP工具.py inputs/backend/tools-deadline.json
```

`tools-normal.json` 给两个调用各设置 0.1 秒服务端延时，最大并发 2；输入文本是 `Archeos and ALKEMIE use HTTP tools.`。结果分别为 6 个空白分词项与 35 个字符；耗时应接近最长一次等待加网络开销，而非固定要求精确为 100 毫秒。

| 文件 | 具体设置 | 应观察的结果 |
| --- | --- | --- |

工具服务为本机教学使用，未加入生产认证和配额，监听回环地址。客户端只允许预定义 path；操作者通过 `--base-url` 配置根地址，不接受模型输入任意 URL。

### 客户端怎样区分几类失败

[并发调用 HTTP 工具.py::call_one](../../../scripts/backend/并发调用HTTP工具.py) 的实际实现如下：

```python
async def call_one(client, call, text, semaphore):
    start = time.monotonic()
    try:
        async with asyncio.timeout(call.timeout_seconds):
            async with semaphore:
                response = await client.post(call.path, json={"text": text, "delay_seconds": call.delay_seconds})
                response.raise_for_status()
                result = {"name": call.name, "status": "ok", "result": response.json()}
    except (TimeoutError, httpx.TimeoutException):
        result = {"name": call.name, "status": "timeout"}
    except httpx.HTTPStatusError as exc:
        result = {"name": call.name, "status": "http_error", "http_status": exc.response.status_code}
    except httpx.RequestError:
        result = {"name": call.name, "status": "network_error"}
    except asyncio.CancelledError:
        raise
    result["elapsed_ms"] = round((time.monotonic() - start) * 1000, 1)
    return result
```

`raise_for_status()` 让 503 变成明确的 HTTPStatusError；TCP 连接失败属于 RequestError；读写等网络阶段的超时属于 HTTPX TimeoutException；外层 `asyncio.timeout` 覆盖排队、请求和读取的整次工具期限。JSON 解码错误等未预料的问题没有被通用 `except Exception` 吞掉，会让 TaskGroup 报告异常并取消同组任务。

HTTPX 的 read timeout 是等待下一块数据的空闲上限，持续有数据到来时整条流仍可能很长；它不等同于总执行时间。四种网络期限的细节见 [HTTPX Timeouts](https://www.python-httpx.org/advanced/timeouts/)。

### 总期限与局部期限为何要分开

调用方复用一个 AsyncClient，并在外层创建 TaskGroup：

```python
async def run_plan(plan, base_url="http://127.0.0.1:8001", transport=None):
    semaphore = asyncio.Semaphore(plan.max_concurrency)
    start = time.monotonic()
    # 网络各阶段的空闲期限与整次工具期限分开设置；trust_env=False 避免本机代理干扰。
    timeout = httpx.Timeout(connect=1, read=3, write=1, pool=1)
    limits = httpx.Limits(max_connections=plan.max_concurrency, max_keepalive_connections=plan.max_concurrency)
    async with httpx.AsyncClient(base_url=base_url, timeout=timeout, limits=limits,
                                 transport=transport, trust_env=False) as client:
        try:
            async with asyncio.timeout(plan.total_timeout_seconds):
                async with asyncio.TaskGroup() as group:
                    tasks = [group.create_task(call_one(client, item, plan.text, semaphore)) for item in plan.calls]
        except TimeoutError:
            # TaskGroup 已取消并等待子任务；外层超时不冒充一组完整的局部结果。
            return {"status": "deadline_exceeded", "elapsed_ms": round((time.monotonic() - start) * 1000, 1)}
    return {"status": "completed", "elapsed_ms": round((time.monotonic() - start) * 1000, 1),
            "results": [task.result() for task in tasks]}
```

这里局部预期错误被转换为数据，因此允许部分成功。外层总期限则取消整组，并等待所有子任务完成取消，再返回 `deadline_exceeded`。它没有把已取消任务强行 `.result()`，也没有把未完成任务称作成功。

`trust_env=False` 用于避免本机代理环境干扰回环地址练习；真实服务如果需要受控代理，应显式配置代理和证书，不能为了连接成功而随意禁用 TLS 验证。

## 用时间线理解并发名额

`tools-partial.json` 的最大并发为 2。前两项先占名额；第三项虽然自身没有服务端延时，也要等第一个调用释放名额。以忽略网络开销的时间线说明：

```text
0ms        words 开始（50ms）        slow 开始（400ms，期限100ms）
50ms       words 返回，名额释放      unavailable 获得名额并返回503
100ms      slow 的等待者超时并取消
```

把局部超时放在 semaphore 外意味着名额等待也算在期限内，防止队列里无限等待。放在内侧则只限制执行时间，需要另外设置排队上限和总期限。连接池上限控制 TCP 连接数量，信号量控制业务同时进行数量，两者相关但不等价。

## 再看线程与进程中的“取消”

以下三种取消对应不同动作，排错时应明确目标：

| 当前工作 | 取消当前 await 后 | 还需做什么 |
| --- | --- | --- |
| 原生异步 HTTP 请求 | 客户端协程退出并关闭相关读取 | 服务端可能已收到请求，核对副作用 |
| `to_thread(sync_sdk)` | 等待者可退出，线程函数可能继续 | SDK 内部期限、合作停止标志或改为独立进程 |
| 已提交远程长任务 | 当前 HTTP 等待结束 | 通过远端任务 ID 查询／取消，并保存确认结果 |

Archeos 的流式入口通过 `asyncio.wait(..., timeout=1)` 定期检查权限。`wait` 返回暂未完成的任务，不像每秒对 `anext()` 使用 `wait_for` 那样反复取消上游读取。理解这些差异后再选择原语，避免把用于“检查状态的轮询周期”误当成“工具只能运行一秒”。

测试异常组时可使用 `python -m pytest -q tests/test_demo.py -k taskgroup`；真实 HTTP 输入文件则检验响应码、连接与序列化路径，两种练习覆盖的边界不同。
