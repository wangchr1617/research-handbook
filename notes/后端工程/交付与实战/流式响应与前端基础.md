# 流式响应与前端基础

**适用环境：通用；后端 Python 3.12／FastAPI，前端使用支持 Fetch 流的现代浏览器。React／TypeScript 为选读。**

## 为什么需要流式响应

普通 JSON 响应通常在处理完成后一次返回，Agent 生成答案时可以逐段输出，让用户更早看到内容和工具阶段。流式传输改善等待体验，但不会自动缩短总计算时间，也不能代替任务状态和结果持久化。

| 方式 | 特点 | 适合用途 |
| --- | --- | --- |
| 普通 JSON | 一次请求一次完整响应 | 配置、历史查询、任务提交与状态 |
| 轮询 | 定期 GET 查询 | 简单任务状态，容易跨代理部署 |
| SSE | HTTP 上单向事件流，文本协议 | Agent delta、工具阶段、状态更新 |
| WebSocket | 建立后可双向持续通信 | 实时协作、交互式控制；需处理认证与重连 |

Archeos 的 run events 接口使用 SSE；ALKEMIE 的恢复模块与 Socket.IO 订阅配合。不要把 Socket.IO 的协议与裸 WebSocket 直接混用。

## SSE 格式

响应类型为 `text/event-stream`，每个事件以空行结束：

```text
id: 42
event: delta
data: {"text":"正在分析材料"}

id: 43
event: done
data: {"status":"succeeded"}

```

`id` 用于续传，`event` 区分类型，`data` 保存文本或 JSON。多行 data 按协议拼接，注释行 `: heartbeat` 可做心跳。协议详见 [MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

HTTP 分块边界、网络读取边界与 SSE 事件边界没有对应关系：一次 `reader.read()` 可能得到半个 UTF-8 字符、半个事件，或多个事件。前端需要增量解码与缓冲，不能直接对每块 `JSON.parse()`。

## 后端发送与资源释放

下面是只演示协议的本机片段；完整应用还需要 Demo 中的认证、事件持久化和权限复查：

```python
import asyncio
import json
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.get("/protocol-example")
async def protocol_example(request: Request):
    async def generate():
        try:
            for i, text in enumerate(["开始", "分析中", "完成"], start=1):
                if await request.is_disconnected():
                    break
                payload = json.dumps({"text": text}, ensure_ascii=False)
                yield f"id: {i}\nevent: delta\ndata: {payload}\n\n"
                await asyncio.sleep(.2)
        finally:
            # 这里释放本生成器拥有的上游连接、文件或迭代器。
            pass
    return StreamingResponse(generate(), media_type="text/event-stream",
        headers={"Cache-Control": "no-store", "X-Accel-Buffering": "no"})
```

保存到独立练习文件并启动后，用 `curl -N http://127.0.0.1:8000/protocol-example` 观察逐段输出。`-N` 关闭 curl 的输出缓冲；代理层同样要关闭响应缓冲。响应头一旦发送，流中发生的错误通常无法再改成另一个 HTTP 状态码，应发送约定的 `error` 事件并结束连接。

Archeos 的 `engine/routes.py::events` 周期性复查会话与成员状态，在 `finally` 关闭上游迭代器与待完成任务。Demo 将 DB 查询放入线程，每轮打开短 Session，查询后关闭，再 yield；不能为了等待下一段文本长期占住数据库连接。

## 持久化、重放与背压

推荐先 `POST /runs` 创建任务，再 `GET /runs/{id}/events` 订阅：worker 独立执行，断开页面只结束订阅，取消执行必须另发取消请求。否则一次 Wi-Fi 断开可能意外杀掉有副作用的任务。

每条事件先写入 `run_events`，再按游标有序读取。Demo 接收 `?after=42`，只返回大于 42 的事件；浏览器保留最后**已处理**的 ID 并按 ID 去重。原生 `EventSource` 自动重连会使用 `Last-Event-ID`，服务端需要显式支持；Demo 使用 Fetch 与查询参数，不自动解释该请求头。

Demo 页面点击“查看事件／重连”会清空显示后从头重放，避免拼出重复文本。若实现自动重连，应采用有上限的退避，401 要求重新登录，404 停止，已终态且事件已读尽时停止重连。

控制单次读取数量、事件大小、并发订阅数、写入速率与保留周期。SSE 发送等待可对当前连接施加背压，但独立 worker 仍可能持续产生事件；真实系统要限制数据库增长，对过期游标返回“需要加载快照”的明确信号。Redis Pub/Sub 只能通知“有新事件”，不能补回客户端离线期间丢失的数据。

## 浏览器调用接口

普通 JSON 请求的最小写法：

```javascript
const response = await fetch('/api/conversations', {
  headers: {Authorization: `Bearer ${token}`}
});
if (!response.ok) throw new Error(`HTTP ${response.status}`);
const conversations = await response.json();
```

`token` 是登录返回的当前页面内存变量。Fetch 遇到 404／500 通常仍正常返回 Response，必须检查 `ok`。使用 Cookie 认证时改为与部署匹配的 `credentials` 选项，写请求还要带 CSRF token。

原生 `EventSource` 不提供任意 Authorization 请求头；Bearer 认证可使用 Fetch 流。完整增量解析、AbortController、错误显示与安全文本渲染见 [Demo 页面](../../../examples/backend/agent-demo/demo/static/index.html)。上传用 `FormData`，不要手工设置 multipart 的 `Content-Type`，浏览器需要自动添加 boundary。

## 前端基础选读

| 技术 | 负责什么 | 在 Demo 中的例子 |
| --- | --- | --- |
| HTML | 页面语义和结构 | 表单、按钮、会话选择框 |
| CSS | 布局、颜色、间距和响应式显示 | 卡片、文本区域、状态提示 |
| JavaScript | 浏览器交互和网络请求 | 登录、Fetch、流解析、更新 DOM |
| TypeScript | 开发时静态类型检查，编译后为 JS | 为 Run、Message 与 props 定义类型 |
| React | 用组件、props、state 描述界面 | 会话列表、消息列表、执行按钮 |

TypeScript 类型不会自动验证服务器 JSON，运行时仍要校验关键数据。React 的状态更新触发重渲染，共享状态可以上提到共同父组件；服务端数据通常由专门的查询缓存管理，不必把所有数据都放入全局状态。

以下组件放在已有 React／TypeScript 项目中，用于说明请求与状态，不要求把 Demo 前端改成 React：

```tsx
import {useEffect, useState} from 'react';

type Message = {id: number; role: string; content: string};

export function History({conversationId, token}: {
  conversationId: string; token: string;
}) {
  const [messages, setMessages] = useState<Message[]>([]);
  const [error, setError] = useState('');
  useEffect(() => {
    const controller = new AbortController();
    setMessages([]); setError('');
    async function load() {
      try {
        const res = await fetch(`/api/conversations/${conversationId}/messages`, {
          headers: {Authorization: `Bearer ${token}`}, signal: controller.signal
        });
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const rows: Message[] = await res.json();
        if (!controller.signal.aborted) setMessages(rows);
      } catch (e) {
        if (!controller.signal.aborted) setError(String(e));
      }
    }
    void load();
    return () => controller.abort();
  }, [conversationId, token]);
  return <section><p role="status">{error}</p>
    {messages.map(m => <p key={m.id}>{m.role}: {m.content}</p>)}
  </section>;
}
```

切换会话时取消旧请求，防止迟到响应覆盖新会话；列表使用稳定的 `key`。流式追加文本使用 `setText(previous => previous + delta)`，避免闭包捕获旧状态。基础概念见 [React Quick Start](https://react.dev/learn)与 [TypeScript 入门](https://www.typescriptlang.org/docs/handbook/typescript-in-5-minutes.html)。

## 用持久事件读一遍真实数据流

运行[请求与恢复实操](../../../examples/backend/agent-demo/请求与恢复实操.md)会生成 `normal-events.sse`。最开始两条事件为：

```text
id: 1
event: status
data: {"status": "queued"}

id: 2
event: status
data: {"status": "running", "attempt": 1}

```

示例 ID 来自新建数据库；已有数据时全局自增值会不同。同一 run 内 ID 有序但未必连续，因为其他 run 也可插入事件。不能把 `id + 1` 不存在当作丢包，应该按 `id > cursor` 查询。

worker 每次把输出切成 6 个 Python 字符写入 delta。第一段可能是 `教学 Age`，下一段是 `nt：并发完`，网络传输又可以任意拆分这些事件，因此前端必须分别处理“UTF-8 字节流”“SSE 帧”“业务文本 delta”三个边界。

### 短数据库查询怎样配合长连接

[main.py::event_page](../../../examples/backend/agent-demo/demo/main.py) 的完整实现：

```python
def event_page(run_id, owner, token_hash, after):
    # 每轮重新创建短事务，同时复查登录是否被撤销；不跨 yield 持有数据库连接。
    with session() as db:
        login = db.get(Login, token_hash)
        if not login or login.expires_at <= time.time() or login.user_id != owner:
            return None
        run = checked_run(db, run_id, owner)
        rows = db.scalars(select(RunEvent).where(RunEvent.run_id == run_id, RunEvent.id > after)
                          .order_by(RunEvent.id).limit(100))
        return run.status, [(row.id, row.kind, row.data) for row in rows]
```

它一次最多取 100 条事件，在关闭 Session 后返回普通数据。SSE 循环等待 0.2 秒时没有持有这个数据库连接；同一登录被撤销后，下一轮返回 None，订阅结束。每轮资源授权也复用 checked_run，而不是以“最初握手成功”作为永久权限。

终态出现时还必须读尽剩余事件。假设 run 已成功但游标落后 205 条，第一轮读 100、第二轮再读 100，第三轮剩 5 条之后才关闭。Demo 用 `status in TERMINAL and len(rows) < 100` 判断最后一页；只检查 status 会让慢客户端漏掉结果末尾。

## 前端怎样正确拆帧

以下是 [index.html::stream](../../../examples/backend/agent-demo/demo/static/index.html) 的真实函数，依赖页面中定义的 token、DOM 辅助函数和状态变量：

```javascript
async function stream(runId) {
  controller?.abort(); controller = new AbortController(); activeRun = runId;
  // 每次从头重放并清空显示；生产前端可存最后已处理 id，传 after 续传并去重。
  $('output').textContent = ''; $('trace').textContent = '';
  const response = await fetch(`/api/runs/${runId}/events?after=0`, {
    headers: {Authorization: 'Bearer ' + token}, signal: controller.signal
  });
  if (!response.ok) throw new Error(`流连接失败：${response.status}`);
  const reader = response.body.getReader();
  const decoder = new TextDecoder(); let buffer = '';
  try {
    while (true) {
      const {value, done} = await reader.read();
      buffer += decoder.decode(value, {stream: !done});
      let end;
      while ((end = buffer.indexOf('\n\n')) >= 0) {
        const frame = buffer.slice(0, end); buffer = buffer.slice(end + 2);
        const lines = frame.split('\n');
        const kind = lines.find(x => x.startsWith('event:'))?.slice(6).trim();
        const data = lines.filter(x => x.startsWith('data:')).map(x => x.slice(5).trimStart()).join('\n');
        if (!data) continue;
        const payload = JSON.parse(data);
        if (kind === 'delta') $('output').textContent += payload.text;
        else $('trace').textContent += `${kind}: ${data}\n`;
        if (kind === 'error') throw new Error(payload.code);
        if (kind === 'done') status(`任务状态：${payload.status}`);
      }
      if (done) break;
    }
  } finally { await reader.cancel(); reader.releaseLock(); }
  await history();
}
```

关键判断分别解决不同问题：

- `TextDecoder.decode(..., {stream: true})` 保留尚未完整接收的 UTF-8 字符。
- `buffer` 保存上次没收齐的帧，只有遇到空行才解析。
- `event` 区分 delta、trace、status、error 和 done，不能把所有事件都追加到答案正文。
- `textContent` 展示模型／用户文本，防止文本被解释成 HTML。
- AbortController 只取消订阅请求；取消 worker 要另发 cancel 接口。
- `finally` 关闭 reader；服务端终态也要正常结束读取，而非永久等下一块。

这段解析器服务于本 Demo 发出的 LF 分隔 SSE 子集；连接任意第三方 SSE 时，还应完整处理 CRLF／CR 分隔、没有 event 时的 message 默认类型和其他协议细节。需要通用 SSE 解析时优先选成熟解析器，不把一个特定服务的简短解析代码宣称为完整协议实现。

### 断线重连的两种界面策略

**从头重放**：清空该 run 的显示，从 `after=0` 读取全部事件。Demo 采用此方式，简单且不重复拼接。

**增量续传**：保存“最后成功处理”的 id，重新请求 `?after=最后id`。持久化 cursor 前先完成该事件的处理；重连边界可能重复投递，按 `(run_id, id)` 去重。不要只保存最后收到的网络块序号。

若令牌失效，应显示重新登录；若任务终态且结果已读尽，不再自动重连。服务端只保留最近事件时，应返回明确的游标过期信号并引导加载快照，否则客户端会永久等待已被裁剪的前缀。

## Archeos 为何保留一个 pending 读取任务

[Archeos events](https://github.com/hfood02/Archeos/blob/275ee9c5edcf4df6c773512d8576cb0010168fd4/backend/archeos/engine/routes.py) 使用以下原始片段：

```python
if pending is None:
    pending = asyncio.create_task(anext(source))
done, _ = await asyncio.wait([pending], timeout=1)
```

这一秒用于回到循环检查身份和断开状态。上游模型可能几秒没有新 token，pending 仍被保留，下一轮等待同一个 task；不能每次超时就再建一个 anext，否则会对同一异步迭代器发起重叠读取。最后在 `finally` 取消待处理 task 并关闭 iterator，防止页面已离开、上游连接却泄露。

ALKEMIE 的恢复快照则在进程内用锁协调写入与订阅读取。一个系统可以同时需要：持久消息保存最终事实、运行快照用于快速恢复显示、事件日志支持游标重放。它们的生命周期不相同，不能只有一个名为 history 的大字典承担全部职责。

## React 状态与服务器事实的边界

把页面中的字段分为三组更容易组织组件：登录状态（内存 token）、服务器资源（会话／消息／run）、临时 UI 状态（输入框、展开状态、当前流文本）。成功提交后将 run_id 保存到当前会话视图，切换会话时取消旧订阅，加载新会话的历史和 run 列表。

真实模型输出可能持续很快，逐 token 调用 React setState 会引起大量重渲染；可在内存缓冲，再按动画帧或短时间片批量刷新。刷新节奏只影响显示，持久事件和 cursor 仍应按协议顺序处理。

接口层负责检查 HTTP 状态、解析错误结构，组件负责 loading／error／empty／ready 的展示。TypeScript 的 `Message` 类型只提供编译期帮助，收到陌生 API 的 JSON 时仍需要运行时解析，不能靠类型断言把坏响应变成正确数据。
