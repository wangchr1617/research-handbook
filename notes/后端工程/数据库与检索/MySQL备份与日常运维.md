# MySQL 备份与日常运维

适用环境：MySQL 8.4、InnoDB；以下命令在本机终端执行，针对[入门练习库](MySQL建模与SQL入门.md)。业务库备份需结合数据规模、权限、GTID、存储引擎与恢复目标设计。

## 连接与账号分工

应用账号按所需库和操作授权，迁移账号负责 DDL，备份账号按备份工具要求授权。连接池设置连接上限、获取超时和失效检测；总连接数要考虑 Web 进程、worker 与运维连接，而不是只看单进程配置。

所有时间字段约定时区。示例中的 DATETIME 本身不携带时区，应用可以统一写 UTC 并在展示层转换；跨服务传输时使用明确偏移。字符集统一使用 `utf8mb4`，标识字段的大小写规则与正文分别设计。

长事务会延长旧版本保留时间并增加锁竞争。排查慢请求时同时查看连接数、事务持续时间、锁等待、磁盘与慢查询，不先通过无限增加连接池掩盖瓶颈。

## 一次可恢复的逻辑备份

下面备份仅包含一个教学库的数据与表结构，不包含全实例账号和授权。先准备可写目录，确认备份文件名尚未占用：

```bash
mysqldump --host=127.0.0.1 --user=YOUR_BACKUP_USER -p \
  --single-transaction --quick --no-tablespaces \
  --set-gtid-purged=OFF handbook_demo > handbook_demo_backup.sql
```

检查退出码及错误输出，不能仅凭文件存在判定成功。`--single-transaction` 为事务表提供一致性快照，无法使非事务表获得同样保障；备份期间避免对相关表执行 DDL。`--set-gtid-purged=OFF` 用于此处独立练习库导出，复制拓扑中的恢复需要另行设计 GTID 策略。[mysqldump 手册](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)还列出了视图、触发器及不同选项所需权限；若业务使用例程或事件，明确将它们纳入备份范围。

在另一测试实例，或确认不存在的恢复练习库中恢复：

```bash
mysql --host=127.0.0.1 --user=YOUR_RESTORE_USER -p \
  -e 'CREATE DATABASE handbook_restore CHARACTER SET utf8mb4'
mysql --host=127.0.0.1 --user=YOUR_RESTORE_USER -p \
  handbook_restore < handbook_demo_backup.sql
```

这份 dump 未使用 `--databases`，便于导入到新库。恢复后检查表结构、约束、关键行、数量及应用查询；备份前若有并发写入，应比较快照对应的数据，而非之后变化的在线计数。还要恢复原始文件或对象存储：仅恢复文档元数据表不能恢复 PDF 内容。

## 从备份恢复到指定时点

恢复点目标 RPO 表示允许丢失的数据时间范围，恢复时间目标 RTO 表示允许服务中断多久。每日 dump 无法独自满足分钟级 RPO。时间点恢复通常先恢复完整备份，再按正确位置或 GTID 应用其后的 binlog，见[官方恢复说明](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-binlog.html)。

备份清单记录版本、选项、范围、时间、binlog 坐标或 GTID、校验摘要及存储位置。备份和日志的保留周期要覆盖恢复窗口；备份异地或独立故障域保存，并按敏感数据管理。复制与副本能帮助可用性，误删也可能被复制，因此仍需独立备份。

## 日常观察哪些信号

| 信号 | 首先判断的问题 |
| --- | --- |
| 慢查询和扫描量增长 | 查询形状、索引、统计信息或数据分布是否变化 |
| 锁等待与死锁增加 | 事务是否变长、资源访问顺序是否改变 |
| 连接耗尽 | 连接泄漏、池上限或慢请求堆积 |
| 磁盘持续增长 | 数据、索引、binlog 与备份分别占多少 |
| 副本延迟 | 查询是否允许陈旧、复制是否阻塞 |
| 恢复演练失败 | 备份是否完整、依赖文件和密钥是否齐全 |

数据库迁移先在恢复副本中演练，测量锁表、耗时和回退条件；应用切换前确认驱动、SQL、排序规则与约束兼容。SQLAlchemy 能统一部分接口，但不能替代跨数据库行为验证。
