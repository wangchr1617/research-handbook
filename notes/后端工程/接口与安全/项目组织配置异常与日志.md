# 项目组织、配置、异常与日志

**适用环境：通用；Python 3.12、FastAPI、Pydantic Settings 2。命令在本机或 WSL 执行。**

## 让职责有固定位置

以 Archeos 为例，`backend/archeos/app.py` 组装应用，`schemas.py` 表达输入输出，`models.py` 定义平台数据，`security.py` 集中认证与授权，`engine/` 连接 Agent 引擎。一个较小的项目可以从以下结构开始，随着业务增长再拆分：

```text
agent-app/
├── app/
│   ├── main.py             # 应用入口、中间件、路由组装
│   ├── api/                # auth、conversations、runs、files
│   ├── schemas/            # HTTP 输入输出模型
│   ├── services/           # 任务提交、权限判断、业务事务
│   ├── repositories/       # 查询与数据访问，规模小时可省略
│   ├── models/             # ORM 数据模型
│   ├── tools/              # 外部 API、模型与受限工具适配
│   ├── worker.py           # 后台队列入口
│   ├── security.py
│   └── config.py
├── migrations/             # Alembic 数据库迁移
├── tests/
├── pyproject.toml          # 元数据、依赖与工具设置
├── .env.example            # 变量名称与无密钥示例
├── Dockerfile
└── compose.yaml
```

路由负责把 HTTP 转成业务输入；服务层判断“这个用户能否在这个会话里启动任务”，并控制事务；工具层负责“如何调用某个模型”。避免在一个路由函数里同时解析请求、拼 SQL、执行 shell、调用模型和写文件。小 Demo 可以少分几层，但仍应把配置、数据、认证、任务和 HTTP 分开。

配套 [Demo](../../../examples/backend/agent-demo/README.md) 使用 `config.py`、`db.py`、`schemas.py`、`security.py`、`jobs.py`、`worker.py` 与 `main.py`，可以逐个阅读而无需先搭完整框架。

## 配置从代码中移出

配置文件适合保存模型名、工具列表、默认超时等结构化信息；环境变量适合注入环境差异；密码、私钥和 API Key 应由受控密钥文件或密钥服务注入。环境变量不是加密保险箱，也可能出现在进程诊断、容器配置和错误日志中。

参照 Archeos `config.py` 的写法：

```python
from functools import lru_cache
from pathlib import Path
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="DEMO_", env_file=".env", extra="ignore"
    )
    data_dir: Path = Path("./data")
    database_url: str = "sqlite:///./data/demo.db"
    tool_api_key: SecretStr = SecretStr("")
    tool_timeout_seconds: int = Field(default=20, ge=1, le=120)

@lru_cache
def settings() -> Settings:
    return Settings()
```

`DEMO_TOOL_TIMEOUT_SECONDS=30` 覆盖默认值。通常初始化参数优先于环境变量，环境变量优先于 `.env`，再到 secrets 目录和默认值；自定义配置源会改变顺序，见 [Settings 官方说明](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)。`env_file` 的相对路径依赖当前工作目录，运行命令时要明确项目目录。

`SecretStr` 避免普通打印直接显示值，调用第三方 SDK 时再显式取 `.get_secret_value()`；主动打印明文仍会泄露。不要把完整 Settings、数据库 URL 或请求头写到日志。

## 区分不同配置文件

| 文件或机制 | 作用 | 使用方式 |
| --- | --- | --- |
| `pyproject.toml`／依赖锁文件 | Python 包、版本和工具配置 | 用隔离环境安装；部署使用验证过的锁文件 |
| `.env` | 本机启动变量 | 不提交，保存无密钥的 `.env.example` |
| Compose `.env` | 对 Compose YAML 做 `${VAR}` 插值 | 不会自动把所有值注入容器 |
| Compose `environment`／`env_file` | 把变量传入容器 | 容器内地址使用服务名，如 `db:5432` |
| Compose secrets／外部密钥服务 | 挂载密钥文件或取短期凭据 | 应用显式读取；控制访问、轮换和审计 |

生产配置至少区分开发、测试和生产数据库，避免测试清空真实数据。新版本上线应先验证配置，再运行一次受控数据库迁移，最后启动 API 和 worker。`create_all()` 适合空库教学，不会替你升级已有表结构。

## 用三个小实验理解配置来源

Demo 的真实配置类位于 [config.py](../../../examples/backend/agent-demo/demo/config.py)：

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="DEMO_", env_file=".env", extra="ignore")
    database_url: str = "sqlite:///./data/demo.db"
    broker_url: str = "redis://127.0.0.1:6379/0"
    session_seconds: int = Field(default=3600, ge=60, le=86400)
    upload_bytes: int = Field(default=65536, ge=1, le=65536)
```

以下命令在 Demo 目录执行，每条都会启动新 Python 进程：

```bash
python -c 'from demo.config import settings; print(settings().session_seconds)'
DEMO_SESSION_SECONDS=120 python -c 'from demo.config import settings; print(settings().session_seconds)'
DEMO_SESSION_SECONDS=10 python -c 'from demo.config import settings; print(settings().session_seconds)'
```

在 `.env` 未覆盖该项时，前两条分别输出 `3600` 与 `120`；第三条在启动阶段发生 ValidationError，因为最低 60 秒。把错误配置提前暴露，比启动后部分请求才异常更好。

`settings()` 有缓存：同一 Python 进程先读取再修改 `os.environ`，旧对象不会自动更新。单元测试需要在修改环境变量后调用 `settings.cache_clear()`；生产修改环境变量通常重启服务。`engine()` 同样缓存了数据库连接配置，不能只清理 Settings 就期望已建的连接池切换目标。

### `.env`、Compose 和容器里分别看到什么

[compose.yaml](../../../examples/backend/agent-demo/compose.yaml) 把 `DEMO_DATABASE_URL` 显式设成 `postgresql+psycopg://...@db:5432/demo`，所以容器不会采用本机 `.env` 中的 SQLite 地址。检查变量时只打印非敏感的解析结果：

```bash
docker compose exec api python - <<'PYCODE'
from urllib.parse import urlsplit
from demo.config import settings
url = urlsplit(settings().database_url)
print({'driver': url.scheme, 'host': url.hostname, 'port': url.port})
PYCODE
```

预期 host 是 `db`，不是 `127.0.0.1`。不要用 `print(settings())` 或无筛选的 `docker inspect` 输出整份连接口令。`.env.example` 留空口令意味着读者需要填入自己的值，不应在公共教程中提供可被误用的通用默认密码。

## 统一异常边界

预期错误使用明确错误码，例如 `not_found`、`quota_exceeded`、`tool_unavailable`。业务层可抛领域异常，由 HTTP 层转换为状态码；后台 worker 则转换为任务状态。不要把所有异常都写成 `200` 加一段错误文本。

```python
from fastapi import HTTPException

def require_budget(remaining: int):
    if remaining <= 0:
        raise HTTPException(status_code=429, detail="quota_exceeded")
```

未预期异常记录堆栈，客户端只看到稳定的错误码和 `request_id`。校验错误仅返回字段路径，避免把密码、全文提示词或上传内容随 `exc.errors()` 原样发到日志与客户端。事务异常后先回滚，不能继续复用处于失败状态的 SQLAlchemy Session。

## 用日志还原一次执行

至少记录时间、级别、服务、`request_id`、`run_id`、工具名、阶段、耗时、错误码和重试次数。HTTP 请求 ID 进入任务记录，再随 worker 日志传播，才能把“点击执行”与之后的工具失败关联起来。工具调用进一步增加 `trace_id`、`span_id`、`parent_span_id`，形成树状调用关系。

```python
import logging
import time

logger = logging.getLogger("agent.tools")
start = time.monotonic()
logger.info("tool_started request_id=%s run_id=%s tool=%s", request_id, run_id, "search")
# 此处执行工具；省略的是具体业务，不是异常边界。
logger.info("tool_finished run_id=%s duration_ms=%.1f", run_id,
            (time.monotonic() - start) * 1000)
```

持久化时间戳使用 UTC 或 Unix 秒，测量耗时使用单调时钟。容器日志输出到 stdout／stderr，由部署环境收集和轮转。生产可使用 JSON 格式及 OpenTelemetry，把指标（队列积压、失败率、P95 耗时）与日志、追踪关联；不要用用户提示词作为指标标签，以免高基数和隐私泄露。

配套 Demo 的事件表保存有限的执行阶段，日志传播请求 ID，属于基础追踪。`/health/ready` 通过只说明数据库与 broker 当前可达，不能证明 worker 存活或真实任务成功，后者需要单独的执行探针。

## 把模块划分落实到一次提交

以 `POST /api/conversations/{id}/runs` 为例，下面各层接收和交出的信息不同：

| 位置 | 接收 | 交出 | 不应顺手承担的职责 |
| --- | --- | --- | --- |
| `schemas.RunInput` | JSON 数据 | 类型明确、长度受限的对象 | 查数据库、授予权限 |
| `security.user_id` | Bearer 凭据 | 服务端认定的用户 ID | 信任请求体自报的角色 |
| `main.submit` | 用户、路径 ID、输入模型 | 持久 run 的 ID 和初始状态 | 在 HTTP 请求内等待整个 Agent |
| `jobs.execute` | 服务端 run ID | 事件、最终消息和状态 | 依赖浏览器连接持续存在 |
| `worker.enqueue` | run ID | 队列消息 | 把整个数据库 Session 放入消息 |
| `db.session` | 运行配置 | 一次短期数据工作单元 | 充当全局并发共享容器 |

遇到需要扩展的业务，先沿这张表定位：新增输出字段改响应模型；改上传策略改上传服务；换模型提供方改工具适配；换数据库改驱动和迁移。这样可以避免在每个路由里重复读取环境变量和拼接认证逻辑。

### 应用入口如何管理长寿命资源

Archeos 的 `app.py::lifespan` 启动科学任务核对循环，并在关闭时先设置 stop，再等待，超时后取消并等待任务；最后关闭独立的本地资源。下面是原函数，所用资源与导入来自 Archeos；不能脱离项目单独启动：

```python
@asynccontextmanager
async def lifespan(app):
    knowledge_logger = logging.getLogger("extension.mineru")
    if not knowledge_logger.hasHandlers():
        handler = logging.StreamHandler()
        handler.setFormatter(logging.Formatter("%(levelname)s: %(name)s: %(message)s"))
        knowledge_logger.addHandler(handler)
    knowledge_logger.setLevel(logging.INFO)
    from .db import session_factory
    from .scientific_tasks import reconciliation_loop, require_continuation_schema
    with storage_lock(ROOT / ".local", exclusive=False):
        stop = asyncio.Event()
        task = None
        if settings().scientific_continuations_enabled:
            with session_factory()() as db:
                require_continuation_schema(db)
            task = asyncio.create_task(reconciliation_loop(stop))
        try:
            yield
        finally:
            stop.set()
            try:
                if task is not None:
                    try:
                        await asyncio.wait_for(task, timeout=5)
                    except TimeoutError:
                        task.cancel()
                        with suppress(asyncio.CancelledError):
                            await task
            finally:
                await asyncio.gather(to_thread(stop_translation), to_thread(stop_access))
```

`stop.set()` 是合作式退出通知；`wait_for` 给正常收尾留时间；`cancel()` 后继续 await，保证取消已经传播。只调用 `cancel()` 就退出进程，会丢掉清理异常和资源关闭。连接池、长期 HTTP 客户端通常也在 lifespan 中创建并关闭，而非每次工具调用都创建一套。

## 从一条错误响应追到 worker

一个失败请求的客户端信息和服务端信息应分开：

```json
{"code":"tool_failed","request_id":"请求追踪标识"}
```

HTTP 错误结构由请求处理器定义；后台任务的 `error_code` 则保存在 run 查询结果里。后台工具失败时，最初 POST 已经返回 202，不能再把当时的 HTTP 状态改成 500。

配套 Demo 的任务日志通过 `request_id` 和 `run_id` 连接。排查步骤：先从 POST 响应头取得 `X-Request-ID`，用它找到提交记录；再按 `run_id` 看 `run_started`、attempt 与错误堆栈；最后对照事件表和最终状态。如果仅有 `enqueue_deferred`，应查 broker 和 dispatcher；如果已有 `run_started`，则查工具与执行期限。

中间件中的 `duration_ms` 在收到响应对象时记录；对于 StreamingResponse，这通常不是整条 SSE 连接持续时间。模型生成耗时、客户端订阅时长和 HTTP 首部响应耗时应分别记录，否则“接口耗时很短”可能掩盖用户实际等待很长。

### 在测试里复现错误边界

```bash
python -m pytest -q tests/test_demo.py -k 'login_logout or timeout_and_failure'
```

`login_logout` 检查 401、422 和会话撤销；`timeout_and_failure` 区分执行超时与普通工具错误，并检查失败时没有创建成功的 assistant 消息。验证异常处理要检查数据库最终状态，不能只检查日志里有没有 ERROR。
