# 集群如何验收、监控与恢复故障

适用环境：Linux 集群；硬件阈值以具体整机与部件手册为准。

验收要分别证明设备符合清单、负载稳定、应用结果正确和多用户流程可用。程序退出码为零只说明这次进程成功结束，不能单独证明数值正确、扩展高效或数据可恢复。

## 按层形成验收记录

| 层次 | 检查内容 | 交付证据 |
| --- | --- | --- |
| 清单 | CPU/内存/GPU/网卡/磁盘料号、序列号、拓扑与固件 | 设备清单、拓扑图与采购差异说明 |
| 单机 | CPU/内存稳定性、ECC、磁盘健康、GPU 错误、热稳态 | 工具版本、测试参数、持续时间、原始日志与传感器记录 |
| 存储/网络 | 持续与并发 I/O、元数据、带宽、延迟、错误计数 | 明确数据集、端点、块大小、缓存条件的测量表 |
| 应用 | 固定输入、数值容差、完成时间、内存、GPU 与并行效率 | 输入校验和、软件构建、启动命令和结果对照 |
| 多用户 | 资源限制、公平策略、GPU 分配、登录与作业权限 | 两个测试账号的申请、占用与限制记录 |
| 恢复 | 节点故障、服务重启、备份恢复与检查点续算 | 恢复步骤、耗时、可恢复到的时间点与校验结果 |

合同约定测试时长和合格阈值，内存与存储测试应覆盖拟交付配置。内存测试、CPU/内存压力测试、GPU 厂商诊断与目标应用各有覆盖范围；HPL 能衡量稠密线性代数，不能代表所有 DFT/MD 性能。不要以某一峰值测试代替应用验收。

磁盘压力测试使用专用临时目录/文件，先确认可用空间、挂载点与清理策略。fio 等工具能破坏数据，禁止把教学配置中的设备名直接用于已有数据盘。测试前后的 SMART、介质错误、网络丢包和 ECC 计数都保留，比较增量与时间关联。

## 应用基准应该记录哪些量

从[现有案例](../../examples/README.md)选已验证输入，再加入团队真实规模任务。比较 CPU 与 GPU 或不同并行布局时，保持方法、精度与收敛标准一致，按应用允许的浮点容差比对能量、力或统计量；不要求所有并行模式逐位一致。

对同一输入测单节点与双节点，对独立任务测同时运行 1/2/4 份的吞吐。报告中写节点、核心、SMT、MPI/OpenMP、绑定、数学库线程、冷/热缓存、重复次数和波动范围。使用[需求笔记](需求分析与预算选型.md)的强扩展效率，同时记录节点小时与 kWh/任务，判断更快是否也更经济。

已配置 Slurm 记账的集群可查询：

```bash
sacct -j 12345 --format=JobID,State,ExitCode,Elapsed,AllocCPUS,ReqMem,MaxRSS
scontrol show node c01
sinfo -R
```

替换作业号和节点名。`MaxRSS` 常见为某个作业步中任务的最大值，不能直接视为所有节点峰值内存之和；查看 `.batch` 和各计算步，结合采集插件定义与每节点监控解释。采样可能漏过瞬时峰值，字段为空也可能来自未启用采集，而非零占用。定义见 [Slurm 记账指南](https://slurm.schedmd.com/accounting.html)。

## 最小可用监控体系

以 Prometheus 采集、Grafana 展示、Alertmanager 路由告警为一种起步方案。Linux 主机用 [node_exporter](https://prometheus.io/docs/guides/node-exporter/)，NVIDIA GPU 用 [DCGM Exporter](https://docs.nvidia.com/datacenter/dcgm/latest/installation/install-dcgm-exporter.html)；BMC/Redfish、SMART/NVMe 与 Slurm 指标另按对应设备和工具接入。使用私网访问控制，采集端点与管理接口不直接暴露公网。

| 指标 | 关注什么 | 告警后的动作 |
| --- | --- | --- |
| 主机存活、时钟 | 节点消失、授时偏差 | 联查交换机/BMC，区分网络与主机故障 |
| 内存与 ECC | 可用内存、OOM、纠错计数增长、不可纠正错误 | 关联 DIMM 与作业；严重错误隔离节点并检修 |
| CPU/GPU | 温度、频率、功率、热降频、GPU Xid/硬件错误 | 结合负载区分功率限制、热问题与硬件故障 |
| 存储 | 容量、inode、延迟、介质错误、SSD 寿命 | 通知数据归属人，扩容/修复，禁止盲目删除 |
| 网络 | 端口错误、丢包、重传、RDMA 拥塞 | 定位端口/线缆，检查 MTU、拥塞和通信后端 |
| Slurm | 队列等待、DRAIN、失败/OOM、资源利用 | 调整申请或修复节点，保留 Reason 与作业日志 |
| 备份 | 最近成功时间、校验与恢复演练 | 失败立即补救，不能只看定时任务是否启动 |

阈值分两类：温度等硬件上限按厂商设定，容量趋势/队列等待按本团队基线设定。教学起点可设项目盘余量低于 15% 持续 15 分钟提醒，再按增长速度调整；同时监控 inode 和预计耗尽时间。

告警应带节点、时间、指标、关联作业和处理手册，设置去重、抑制与维护静默，指定接收人与响应时限。

## 按现象排查，而不是反复重启

| 现象 | 检查顺序与可能原因 | 有条件的处理与复查 |
| --- | --- | --- |
| Slurm 节点 DRAIN | `sinfo -R`、节点 Reason、slurmd 日志、资源报告 | 修正资源/硬件故障后再恢复；提交小作业验证 |
| CPU 满但任务更慢 | MPI×OpenMP×BLAS 线程、SMT、NUMA、频率 | 减少超额线程并绑定，比较相同输入耗时 |
| `OUT_OF_MEMORY` | ReqMem、作业步记录、节点可用内存、应用规模 | 修正申请或算法布局；不能只加 swap，复测内存与结果 |
| GPU 利用率低 | CPU 喂数、数据读取、batch、同步与后端 | 先定位瓶颈，再调整；比较端到端吞吐与误差 |
| MPI 跨节点卡死 | 认证/名称、MPI/PMIx、传输层、防火墙、MTU | 从双节点最小 MPI 起恢复，复查实际通信路径 |
| 磁盘有空间却写失败 | inode、配额、权限、只读挂载和介质错误 | 按原因处理，使用同用户测试写入并校验 |
| 长作业后段变慢 | 热降频、SSD 缓存耗尽、写放大、共享 I/O | 看时间序列，再分别隔离负载复测 |
| 共享盘失联后系统盘满 | `findmnt`、挂载依赖、误写目录 | 停相关作业，定位数据后恢复挂载，确认无覆盖再搬移 |

处理硬件故障时先将节点 DRAIN，允许现有作业按策略结束或保存检查点，记录故障现场；更换部件后重跑相关验收再恢复接单。共享存储故障需先保护数据，避免多个管理员同时尝试不一致的修复。

## 把日常维护做成可交接的记录

每日看故障、备份与容量趋势；每周看队列、资源浪费和错误增长；按计划检查备件、保修、恢复演练和安全更新。更新先在备用节点验证应用、MPI、驱动与调度链，再安排维护窗口滚动实施。操作记录包含原因、改动、旧版本、验证与回滚；口令和密钥放专门的受控存储。

交接包至少包括物料/序列号、网络与电源拓扑、主机角色、版本清单、配置模板、用户权限规则、备份策略、告警接收方式、恢复步骤与供应商联系人。用新管理员从备份重建一个练习节点，能够重新提交并完成基准作业，才说明文档足以支持基本运维。
